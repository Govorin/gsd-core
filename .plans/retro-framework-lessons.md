# План: ретро учит не только проект, но и GSD (2026-10-28)

## Почему

Ретро polyglot 2026-10-28 (cand-1) нашло 68 повторных ошибок из 72. Все они — отказы Claude Code в
worktree-сессиях. У ретро был только один адресат, проект, поэтому кандидат получился записью в
заметке проекта. Причину ретро назвало верно («лучшее место — вне проекта, патча нет»), но
отправить её было некуда. Проверка 2026-10-28 (`.plans/worktree-isolation-verifier.md` в ветке
`fix/secret-guard-grep-pattern`) показала, что настоящий корень в ядре GSD: загрузчик `gsd_run`,
`worktree_branch_check`, проверки 0a и 0b — всё это формы, которые Claude Code ≥ 2.1.310 отклоняет.
Та же беда повторится в любом репозитории, где GSD исполняет фазы в worktree.

Второй урок: ретро 2026-10-25 предлагало строку в CLAUDE.md, её не применили, и число отказов
выросло с 7 до 68. Ретро не видит судьбу своих прошлых предложений.

## Решение (поправка §10 к ADR-5209)

### 1. У каждого кандидата есть слой, которому принадлежит причина

Новое обязательное поле `layer`:

| Слой | Где правка | Пример |
|---|---|---|
| `project` | файлы этого репозитория (как сейчас) | правило линтера, строка в CLAUDE.md проекта |
| `user` | настройки пользователя вне репозитория: `~/.claude/settings.json`, хуки, личные скиллы, глобальный CLAUDE.md | хук `SubagentStart` с правилами worktree |
| `gsd` | отгружаемая поверхность GSD: агенты, workflow, references, хуки, CLI | загрузчик `gsd_run` отклоняется в worktree |
| `host` | поведение самого рантайма (Claude Code и др.); исправить можно только обходом | проверка изоляции worktree в 2.1.310 |

Тест на повторяемость, новый шаг аналитика: «повторится ли это трение без изменений в другом
репозитории с той же установкой GSD и тем же рантаймом?» Если да, слой не `project`. Тогда
аналитик пишет кандидата нужного слоя. Временную меру для проекта он может дать отдельным
кандидатом `project`, и оба кандидата ссылаются друг на друга через `related`.

Проверка кодом (`validateCandidates`), кандидат с нарушением отбрасывается:
- `layer` должен быть одним из четырёх.
- `gsd`: `target` — путь внутри установленного GSD (`gsd-core/…`, `agents/…`, `hooks/…`,
  `commands/…`), и такой файл существует под корнем установки (корень передаётся в бандл:
  `gsd.root`, `gsd.version`).
- `host`: в `target` указано имя рантайма и версия из бандла (`host.name`, `host.version`).
- `user`: `target` лежит под домашним каталогом и вне корня проекта.
- `project`: `target` внутри проекта (как сейчас).
- Маршрут `--apply` зависит от слоя (см. п. 3).

### 2. Журнал уроков, общий для всех репозиториев

`${GSD_HOME||homedir()}/.gsd/lessons/LESSONS.json` — тот же принцип хранилища пользователя вне
репозитория, что у `capability-consent.cts`. Запись — с блокировкой, как `RUNS.json`; при битом
журнале — fail closed с кодом `lessons-invalid`.

Урок: `id` (`lesson-<hash>`, hash от `layer` + нормализованного `target` + `title`), `layer`,
`target`, `title`, `change`, `status` (`open` | `fixed` | `wontfix`), `fixedIn` (версия GSD или
рантайма), `occurrences[]` — `{project, retro, candidate, date, signals[], gsdVersion,
hostVersion}`. Для `gsd` и `host` — `draft`: готовый текст issue (что, доказательство, где,
предложение). Отправлять его или нет, решает человек; форк ничего не отправляет.

CLI: `gsd-tools retro lessons [--json] [--layer X] [--status Y]`,
`retro lessons record --retro <stem> --candidate <id>` (из кандидата `user`/`gsd`/`host`),
`retro lessons close --id <lesson> --status fixed|wontfix [--fixed-in <ver>]`.

Бандл ретро получает открытые уроки (`lessons[]`, урезанные до заголовка, слоя, цели и числа
повторений). Если сигнал совпадает с открытым уроком, аналитик пишет кандидата с ссылкой
`lesson:<id>` в `signals`; такая ссылка допустима как доказательство. При `--apply` повторение
добавляется к уроку, а не создаётся дубль. Число повторений по проектам задаёт приоритет. Если
урок `fixed` в версии ≤ текущей, а сигнал повторился, это регрессия: урок снова `open`, в отчёте
пометка.

### 3. Маршрут `--apply` по слою

- `project`: как сейчас (`/gsd-quick` или `/gsd-capture`).
- `user`: показать патч и цель и спросить человека. Правка файла пользователя — только с его
  явного «да», после этого вызов `retro lessons record`. Ретро само ничего не применяет (§5 ADR).
- `gsd`, `host`: `retro lessons record`. Проект не трогается. Человеку — путь к уроку и к
  черновику issue.

### 4. Ретро видит судьбу своих прошлых предложений

Код (не модель) сравнивает сигналы текущего отчёта с кандидатами прошлых ретро этого проекта
(`.planning/retro/RETRO-*.json`, совпадение по id сигнала: он хэш ключа и между прогонами
стабилен). В бандл попадает `recurring[]` — `{retro, candidate, applied: bool, countThen,
countNow}`. Признак `applied` берётся из `RUNS.json`, `CHECKS.json` или журнала уроков. Аналитик
обязан разобрать каждую запись `recurring` в разделе отчёта «Предлагалось раньше». Если
предложение не применили, а сигнал вырос, кандидат получает `severity: high` и ссылку
`retro:<stem>:<cand>`. Если применили, а сигнал повторился, правка не сработала, и её надо
пересмотреть, а не повторять.

### 5. Что не меняется

Ретро по-прежнему ничего не применяет само. Доказательства — только из бандла. Приватность (§3)
та же: в журнал уроков попадают только id сигналов и короткие ключи, без выдержек из транскрипта.

## Где правки

- `src/retro-artifacts.cts`: `CANDIDATE_LAYERS`, поле `layer`, `related`, проверки по слою,
  маршрут по слою, ссылки `lesson:`/`retro:` в индексе доказательств.

- `agents/gsd-retro-analyst.md`: таблица слоёв, тест на повторяемость, раздел «Предлагалось
  раньше», схема кандидата.
- `gsd-core/workflows/retro.md`: шаг `apply_candidate` по слоям, показ уроков
  (`--lessons`).

## Первые уроки после слияния

1. `gsd`: shell-блоки ядра (`gsd_run`, `worktree_branch_check`, 0a, 0b, 0p) не проходят
   проверку изоляции Claude Code ≥ 2.1.310. Цель — `gsd-core/references/gsd-run-resolver.md`.
2. `host`: Claude Code 2.1.310+ отклоняет в изолированном worktree git и node с вычисляемыми
   аргументами; обход — литеральные пути и глаголы CLI.
3. `user`: хук `SubagentStart`, который доставляет правила worktree агентам `general-purpose`.

## Отклонения (реализация 2026-10-28)

1. **Повторы ищутся по отпечатку сигнала, а не по id.** План исходил из того, что id сигнала — хэш
   ключа и стабилен между прогонами. Это не так: `signalId` (`src/retro-signals.cts`) хэширует
   `kind`, `key` и **первый указатель** (`file:line` транскрипта), так что то же трение в новой
   сессии получает новый id, и сравнение по id не нашло бы ни одного повтора. Сравнение идёт по
   `signalFingerprint(kind, key)`. `.work/`-бандл живёт только в checkout, где ретро шло (у
   polyglot бандл 2026-10-25 к 2026-10-28 уже пропал), поэтому `retro prepare` пишет на запуск в
   RUNS.json `signals[]` — `{id, fingerprint, count}`, не больше 100, только хэши и счёты, без
   ключа и текста. Прошлое ретро читается через свой запуск, иначе через бандл; без обоих (ретро до
   §10 с пропавшим бандлом) не угадывается, а называется в `recurring.unreadable`. Сигнал без
   ключа отпечатка не имеет и не сравнивается.
2. **`applied` пишется в RUNS.json новым глаголом `retro applied`.** План перечислял RUNS.json как
   источник, но ничто туда отметку о применении не писало: кандидаты, ушедшие в `/gsd-capture`
   (как cand-1 от 2026-10-25), не оставляли следа нигде. Теперь у запуска ретро есть
   необязательный `applied[]` (`candidate`, `route`, `at`); пустой не пишется, старые журналы не
   меняют байты. Отдельный `APPLIED.json` отвергнут: запуск и есть ретро, а у RUNS.json уже есть
   блокировка и чтение fail closed.
3. **Маршрут `user`: ретро не правит файл пользователя даже после «да».** Workflow показывает цель,
   изменение и патч; после явного «да, применил» — `retro lessons record`. У команды нет инструмента
   правки, а второе основание §5 (агент не пишет правила, которые его связывают) к личным
   настройкам относится тем более.
4. **Поверхность `gsd` уже, чем в плане, и шире на `skills/gsd-`.** Префиксы: `gsd-core/`,
   `agents/gsd-`, `hooks/gsd-`, `commands/gsd/`, `skills/gsd-`. В установке Claude Code команды
   лежат скиллами (`~/.claude/skills/gsd-*`, `commands/gsd` нет), а в `agents/` и `hooks/` лежат и
   собственные агенты и хуки пользователя — это слой `user`.
5. **Корень GSD для проверки берётся у запущенного `gsd-tools`, а не из бандла.** Бандл пишет
   `gsd.root`/`gsd.version` для аналитика, но валидатор вычисляет корень сам
   (`resolveGsdInstall`: `gsd-core/bin/lib/../../..`, версия — правилом `runtime-identity`): у
   аналитика есть Write, и бандл не должен быть источником правды для проверки его же утверждений.
   `host.name`/`host.version` берутся из бандла: транскрипт читает только `prepare`.
6. **Версия рантайма.** `SessionTranscript.hostVersion` — поле `version` последней записи основного
   транскрипта, которое его несёт (сессия через обновление сообщает новую версию). Формат цели
   `host`: `<runtime>@<version>[: <area>]`; без известной версии — `<runtime>[: <area>]` с пометкой
   `notes: ["host-version-unknown"]`, а заявленная версия при неизвестной отбрасывается.
7. **`verify` обязателен только для `project` и `user`.** Проверка `gsd`/`host` проверяется там, где
   ложится, а не в этом проекте; refuter запускается только для `route: quick`.
8. **Повтор проверяется кодом, не только промптом.** Кандидат, чьи сигналы — это трение из
   `recurring`, обязан сослаться на `retro:<stem>:<cand>` (`recurring-uncited`), а при
   `escalate` — быть `high` (`recurring-not-escalated`). Прозой это правило уже один раз не
   сработало (7 → 68).
9. **Типизированные коды отказа.** У каждого `dropped` теперь `codes[]` параллельно `reasons[]`
   (`CANDIDATE_DROP`); старые тесты переведены с regex по тексту на коды.
10. **Журнал уроков строже CHECKS.json.** Одна битая запись делает весь журнал `lessons-invalid`
    (CHECKS.json пропускает битую запись): иначе следующая запись начала бы нечитаемый урок заново,
    а перезапись стёрла бы его. Ошибка записи — новый код `retro_lessons_invalid`
    (`ERROR_REASON.RETRO_LESSONS_INVALID`, исход UNAVAILABLE).
11. **Проект урока — корень основного worktree**, `~`-свёрнутый: worktree одного репозитория
    считаются одним проектом. В черновике issue проект назван только именем каталога.
12. **Раздел отчёта** назван «Proposed before» (отгружаемые промпты на английском).

### Отклонения после ревью (2026-10-28, вторая итерация)

13. **Отпечаток считается в retro-signals из идентичности группы, пути маскируются.** Первый
    вариант хэшировал `kind + key`, а `key` у `repeated-tool-error` — «первая команда → ошибка»:
    на бандле polyglot 16 сигналов cand-1 дали 16 разных отпечатков при одной стене. Теперь
    `fingerprint` лежит в сигнале отчёта: ошибка — инструмент + текст ошибки до первого пути (пути →
    `<path>`); отказ — инструмент + первые слова первого сегмента команды; nav-streak — один
    отпечаток. Обрезка до первого пути выбрана, а не «первые 100 символов после маскирования»: старый
    ключ обрезан на 100 символах до маскирования, и иначе старые бандлы не совпали бы с новыми
    сессиями. Цена: две ошибки, различающиеся только текстом после пути, совпадут, если перед путём
    не меньше 12 символов. На копии polyglot: 19 сигналов cand-1 → 6 отпечатков (16
    `repeated-tool-error`, 68 ошибок → 1); симулированная следующая сессия (другая первая команда,
    другой worktree) совпадает 19 из 19.
14. **`omitted` журналируются** (минор 9): на них можно ссылаться (они в `evidence`), значит, их
    надо узнавать потом и подставлять как доказательства без бандла. В отчёте у `omitted` теперь
    `count` и `fingerprint`; в RUNS.json — до 100 записей, сначала перечисленные.
15. **Урок `gsd`/`host` — «применено» только когда `fixed`**; `user` — сразу (его записывают после
    «да, применил»). У `recurring` есть `lesson`, у аналитика четыре случая; открытый урок требует
    `lesson:<id>` (`recurring-lesson-uncited`), если урок есть в журнале.
16. **Валидация не верит бандлу**: `host.*` и `gsdVersion` — из запуска в RUNS.json, `recurring` и
    доказательства-уроки пересчитываются из журналов, из бандла — только ids, которые видел
    аналитик. Без бандла ids сигналов берутся из запуска; `retro applied` проверяет только, что
    кандидат есть в RETRO-*.json и у стема есть запуск.
17. **RUNS.json пишется с `version: 2`.** Старый `gsd-tools` переписал бы журнал без новых полей;
    версию 2 он не читает и потому ничего не переписывает (fail closed, его расписание на паузе).
    Версия 1 читается, следующая запись её обновляет.
18. **`--apply`/`--checks`/`--lessons` минуют `prepare`**, где определяется `gsd_run`: workflow
    велит сначала выполнить резолвер (ссылкой на `gsd-run-resolver.md`, без копии). `STEM` для
    `--apply` берётся через `retro candidates --id … --pick retro`.
19. **Приватность черновика**: проекты пронумерованы, в `title`/`target`/`change` пути → `<path>`,
    путь и имя каждого проекта → `<project>`; `private-path` и `field-too-long` отбрасывают кандидатов
    `gsd`/`host` до журнала. Черновик пишется раньше журнала (`draft-unwritable`).

### Отклонения после второго ревью (2026-10-28, третья итерация)

20. **Валидация — по снимку `prepare`** (N1). На запуске в RUNS.json лежит `snapshot`
    (`inventory`, `checks`, `lessons`, `recurring` — как видел аналитик); `recurring` не
    пересчитывается при валидации. Из настоящего проверяется только, что упомянутый урок существует.
    Запуск без снимка (записан до этой правки) повтором ничего не требует. Контрольную сумму снимка
    не добавлял: аналитик, способный переписать RUNS.json, перепишет и её; в ADR честно записано, что
    граница держится на запрете промпта и на порядке (код пишет всё до запуска аналитика).
21. **Отпечаток ошибки — весь замаскированный текст**, а не «до первого пути» (N2): хвост после пути
    часто и называет ошибку (у polyglot: «…<path>, but this command runs sed…»). Маскируются пути
    (вкл. Windows), URL, все числа, `$VAR`; база обрезается на 200. Совместимость со старыми ключами
    (обрезаны на 100 до маскировки) больше не утверждается — она best effort; надёжный источник —
    отпечатки на запусках.
22. **Слабый отпечаток** (`fingerprintWeak` / `weak`): `Exit code N`, URL, только пути и
    слова-наполнители. Он различается тем, что скрыла маскировка (имена файлов, хост), и формой
    вызова; в `recurring` показывается (`weak`, `weakSignals`), но `recurring-uncited`,
    `recurring-not-escalated` и `recurring-lesson-uncited` к нему не применяются.
23. **Форма вызова**: первая содержательная команда (без `cd` и `VAR=`), имя + флаги + подкоманда
    для git/npm/…; `git` — подкоманда после глобальных опций; файловые инструменты — место
    (`project`/`home`/`outside`) и расширение. Простые аргументы в форму не входят: `cat a` и `cat b`
    — один отказ.
24. **RUNS.json остаётся `version: 2`** (минор 5): установленный 1.18.0 при `version: 1` терпит
    неизвестные поля при чтении, но при записи их выбрасывает — тихая потеря `signals`/`applied`/
    `snapshot`. Отказ старого инструмента (`journal-invalid`, пауза расписания) лучше потери. Версия
    новее известной — отдельная причина `journal-newer` (расписание, ответ stage, отказ `applied`).
25. **`retro applied` принимает только валидного кандидата** (минор 8), а валидация без бандла
    опирается на снимок запуска (минор 7).

### Отклонения после третьего ревью (2026-10-28, четвёртая итерация)

26. **Легаси-факты сравниваются только с легаси-отпечатком** (N3). Факты ретро до §10 строятся из
    ключа (обрезан на 100 до маскировки) и помечаются `legacy`; текущие сигналы несут
    `legacyFingerprint` из своего ключа. Ревьюер предложил сравнивать `fingerprintBasisFromKey` на
    обоих ключах как есть, но новый ключ режется на 100 символах в другом месте, если путь worktree
    другой длины; поэтому легаси-база — замаскированная ошибка до первого пути включительно, где оба
    ключа совпадают. Легаси-отпечаток хэшируется с префиксом `legacy`, с полнотекстовым он не
    совпадает никогда. На копии polyglot: новая сессия с полными текстами отказа в другом worktree —
    14 из 14 (без правки 0).
27. **Числа** (минор 1): маскируются отдельные числа; цифры внутри идентификаторов остаются;
    трёхзначный статус после `status`/`code`/`HTTP` остаётся — 404 и 500 меняют смысл, номер строки
    нет. Цена: `Exit code 127` и `128` различаются, `1` и `2` — нет.
28. **Интерпретаторы** (минор 2): форма — имя файла скрипта. **Лимиты** (минор 3): у записи
    `recurring` до 20 ids, снимок `recurring` — до `MAX_RECURRING`. **Ссылки** (минор 5) длиннее 400
    при записи запуска выбрасываются, запуск остаётся валидным. **Снимок** (минор 4): inventory и
    checks — из снимка, когда он есть. Флаг `weak` сигнала теперь сохраняется в RUNS.json (раньше
    терялся при записи).
