# 3.13 — `gsd-worktree-provision` по контракту `WorktreeCreate`

Исследование 2026-10-04 (документация Claude Code: https://code.claude.com/docs/en/worktrees.md,
раздел non-git version control; issue #27467).

## Контракт
- Срабатывает на `claude --worktree <name>`, инструмент `EnterWorktree`, `isolation: "worktree"` у агентов.
- **Полностью заменяет** встроенное `git worktree add`: хук сам создаёт checkout.
- stdin: JSON; документировано только поле `name`. Прочие поля не документированы — читать
  `name` и не полагаться на остальное (логировать всё входящее в stderr при `GSD_DEBUG`).
- stdout: **только** абсолютный путь созданного worktree. Любой иной вывод в stdout → ошибка или
  зависание (#27467). Все логи — в stderr.
- exit 0 — успех, путь используется как рабочая директория; ненулевой — создание отменяется.
- timeout — из конфига хука (по умолчанию 600 с).
- `.worktreeinclude` при хуке не обрабатывается — копирование файлов делает хук.
- `WorktreeRemove` — только очистка, блокировать не может; вход содержит путь.
- Конфигурируется в `settings.json` (проект/глобально), без matcher-ов. Поддержка в плагинном
  `hooks/hooks.json` по документации — нет; `claude plugin validate --strict` имя события принимает
  (проверено W2) — противоречие, регистрировать через установщик в `settings.json`.

## Почему сейчас не работает
Текущий хук только снаряжает (deps, tools) и путь не печатает → при регистрации на `WorktreeCreate`
ломает любое создание worktree. Поэтому он нигде не зарегистрирован, и функция «снарядить worktree при
создании» фактически отсутствует.

## Побочная находка
Встроенный механизм создаёт worktree агентов от `origin/HEAD`. В этом форке `origin` — GitHub-форк
владельца, отставший на ~900 коммитов, поэтому изолированные агенты получали базу `d2ae7fe39`.
Свой хук создаёт worktree от **локального HEAD** — это и правильнее, и снимает проблему.

## Дизайн реализации
1. Прочитать `name` из stdin (валидировать: только `[A-Za-z0-9._-]`, без `..`).
2. Корень репозитория: `git rev-parse --show-toplevel` от cwd хука. Путь: `<root>/.claude/worktrees/<name>`
   (совпадает с поведением встроенного механизма, которое видно по `isolation`-агентам).
3. Ветка `worktree-<name>` от локального `HEAD` (`git worktree add -b worktree-<name> <path> HEAD`);
   если ветка/путь уже существуют — переиспользовать идемпотентно или выдать понятную ошибку.
4. Снаряжение (существующая логика provision: зависимости, инструменты, `workflow.worktree_*`) —
   после создания, логи в stderr; провал снаряжения — решить политику по конфигу
   (`workflow.worktree_provision`: fail → exit≠0 с причиной в stderr; по умолчанию — предупреждение).
5. stdout: `process.stdout.write(absPath)` и ничего больше.
6. Парный `WorktreeRemove`: `git worktree remove --force <path>` + удаление ветки, если она слита/пустая.
7. Регистрация — установщиком в `settings.json` (не в плагинном манифесте), с timeout под снаряжение.

## Приёмка
- Тест: вход `{"name":"x"}` в temp git repo → worktree создан от HEAD, stdout ровно путь, exit 0.
- Тест: невалидное имя / существующий путь → exit≠0, stdout пуст, причина в stderr.
- Тест: провал снаряжения при включённом строгом режиме → exit≠0; при выключенном — предупреждение.
- Тест: `WorktreeRemove` убирает worktree и ветку.
- Живая проверка: `isolation: "worktree"` у агента получает базу = локальный HEAD.
