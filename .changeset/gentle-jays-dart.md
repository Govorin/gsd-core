**The secret read guard no longer denies a grep regex as a Windows path** — `ls -a | grep -i "^\.env"` was denied as a read of `.env`: the guard judged the pattern of `grep`/`egrep`/`fgrep` as a file name, and its Windows-path split cut the quoted `^\.env` at the backslash. The pattern position (the first positional word, or each `-e`/`--regexp` value before any positional) is now judged on its POSIX `/` segments only, so a regex like `^\.env` or `\.env` passes while a bare `.env` there is still denied — `grep -e .env README.md` stays blocked, a stated false positive that keeps any misparse down to a `\`-bearing word. File operands, `-f`/`--file` values, option values and input redirects keep the full check, and the full check returns on an option outside the GNU/macOS grep vocabulary, a bare `--context`, an `-e` after a positional, or a substitution anywhere in the command's words. Riding along: a substitution or unquoted glob/brace in a segment now withdraws the `--env-file` / git-pathspec / `cp`/`mv`-destination name-only positions, and one in a wrapper word before the command (`timeout {1,cat} ls .env`, `timeout {1,cat} cp x .env`) also withdraws the non-reading exemption, since it can change which command runs; `cp "$@" .env` is now denied. The same holds for a substitution in the command word itself (`X='cat /bin'; $X/ls .env` runs `cat`), while leading `VAR=value` assignments never count, since bash neither splits nor globs their value (`ROOT="$PWD" ls .env` passes). `file` is non-reading only with its classify options: `file -f .env`, `file --files-from .env`, `file -m .env x` and `file -M .env x` print the file's lines and are now denied, and any other option or a substitution keeps a `file` command checked (fork:secret-guard-grep-pattern).
