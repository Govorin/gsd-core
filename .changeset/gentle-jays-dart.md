**The secret read guard no longer denies a grep regex as a Windows path** — `ls -a | grep -i "^\.env"` was denied as a read of `.env`: the guard judged the pattern of `grep`/`egrep`/`fgrep` as a file name, and its Windows-path split cut the quoted `^\.env` at the backslash. The pattern position (the first positional word, or each `-e`/`--regexp` value before any positional) is now judged on its POSIX `/` segments only, so a regex like `^\.env` or `\.env` passes while a bare `.env` there is still denied — `grep -e .env README.md` stays blocked, a stated false positive that keeps any misparse down to a `\`-bearing word. File operands, `-f`/`--file` values, option values and input redirects keep the full check, and the full check returns on an option outside the GNU/macOS grep vocabulary, a bare `--context`, an `-e` after a positional, or a substitution anywhere in the command's words. Riding along: a substitution or unquoted glob/brace in a segment now withdraws the `--env-file` / git-pathspec / `cp`/`mv`-destination name-only positions, and one in a wrapper word before the command (`timeout {1,cat} ls .env`, `timeout {1,cat} cp x .env`) also withdraws the non-reading exemption, since it can change which command runs; `cp "$@" .env` is now denied. The same holds for a substitution in the command word itself (`X='cat /bin'; $X/ls .env` runs `cat`), while leading `VAR=value` assignments never count, since bash neither splits nor globs their value (`ROOT="$PWD" ls .env` passes). `file` is non-reading only with its classify options: `file -f .env`, `file --files-from .env`, `file -m .env x` and `file -M .env x` print the file's lines and are now denied, and any other option or a substitution keeps a `file` command checked; that includes the debug options `-D` (macOS) and `-d` (GNU), which print the bytes each magic test read. A `VAR=value` word counts as an assignment only when its name and `=` are unquoted and unescaped, so `"X"=/bin/cat .env` (a command reached through a directory named `X=`) is checked as the command it is. Words the shell expands are now unrolled and judged: brace alternatives and sequences (`cat .e{n,}v`, `{cat,.env}`, `timeout {1,cat,.env}`, `cat .e{m..o}v`, denied `glob-too-complex` past 64 alternatives; a numeric sequence counts as one), globs whose last segment starts with a literal `.` by the Grep tool's glob rule (`cat .en[v]`, `cat .e*`, `cat < .e*`, `cat .*rc`), and glued `(…)` groups in their zsh alternation, zsh glob-qualifier and bash-extglob readings (`cat .e(nv|x)`, `cat @(.env)`, `cat .env(N)`, `cat *(D)`); `ls .env*`, `[ -f .env ]`, `cp {} .env`, `cat *` and `cat *.*` still pass, since bash and zsh keep a leading dot out of `*` by default (fork:secret-guard-grep-pattern).
