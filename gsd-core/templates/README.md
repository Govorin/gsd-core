# GSD Canonical Artifact Registry

This directory contains the template files for every artifact that GSD workflows officially produce. The table below is the authoritative index: **if a `.planning/` root file is not listed here, `gsd-health` will flag it as W019** (unrecognized artifact).

Agents should query this file before treating a `.planning/` file as authoritative. If the file name does not appear below, it is not a canonical GSD artifact.

---

**Two different sets live in this file. Do not conflate them.** The generated **Template Index**
immediately below lists **template files** — what ships in `gsd-core/templates/` — together with the
registry metadata each one declares in its `gsd-template:` block (specified in
[`docs/reference/template-registry.md`](../../docs/reference/template-registry.md)). Every section
*after* it lists the **artifacts** those workflows produce. The two sets do not correspond: most
`CANONICAL_EXACT` artifact names (13 of 19 when this was written) have no template file at all, and several templates produce no
`.planning/` root artifact. **A missing template is not a missing artifact** — an agent that reads
absence from the index as absence of the artifact will wrongly flag real planning state.

**What the generated index did and did not replace.** It replaced the hand-maintained template list
in `docs/ARCHITECTURE.md` §Templates outright. It did **not** replace the artifact tables below, and
no row was deleted for it: each of those rows keys on an *artifact* name or pattern (`NN-MM-PLAN.md`,
not `plan.md`) and carries a `Produced by` workflow and a `Purpose` sentence that the five-key block
cannot express — as do the reserved-name warning for `BACKLOG.md`/`THREADS.md` and the three notes
under the host table. `config.json` is deliberately outside the registry: it is JSON and cannot carry
markdown frontmatter, so the generator treats a non-`.md` file as out of scope by construction. Its
artifact row below is unaffected.

## `.planning/` Root Artifacts

These files live directly at `.planning/` — not inside phase subdirectories.

|------|----------|-------------|---------|
| `PROJECT.md` | `project.md` | `/gsd:new-project` | Project identity, goals, requirements summary |
| `ROADMAP.md` | `roadmap.md` | `/gsd:new-milestone`, `/gsd:new-project` | Phase plan with milestones and progress tracking |
| `STATE.md` | `state.md` | `/gsd:new-project`, `/gsd:health --repair` | Current session state, active phase, last activity |
| `REQUIREMENTS.md` | `requirements.md` | `/gsd:new-milestone` | Functional requirements with traceability |
| `MILESTONES.md` | `milestone.md` | `/gsd:complete-milestone` | Log of completed milestones with accomplishments |
| `BACKLOG.md` | *(none)* | ⚠ **nothing** — see note | Pending ideas and deferred work |
| `LEARNINGS.md` | *(inline)* | `/gsd:extract-learnings`, `/gsd:execute-phase` (gated: `features.global_learnings`) | Phase retrospective learnings for future plans |
| `THREADS.md` | *(none)* | ⚠ **nothing** — see note | Persistent discussion threads |

> ⚠ **`BACKLOG.md` and `THREADS.md` are reserved names, not files GSD creates.** Both are members of
> `CANONICAL_EXACT` (locked by `tests/artifacts.test.cjs`), so a file with either name is treated as
> canonical planning state and protected from cleanup — but no workflow writes either one:
>
> - **Backlog** lives in `ROADMAP.md` as `## Backlog` with phase entries numbered `999.x`
>   (`/gsd:capture --backlog` → `add-backlog.md`), and is promoted from there by
>   `gsd-review-backlog`. There is no second backlog file; do not create one, or the two will
>   diverge with no reconciler.
> - **Threads** live in the `.planning/threads/` **directory**, one `{slug}.md` per thread
>   (`/gsd:thread` → `thread.md`). The singular `THREADS.md` registry entry predates that layout.
>
> Keeping both in `CANONICAL_EXACT` is harmless (it protects the name if a project creates it by
> hand) and removing them would red the artifacts test. The defect was this table implying a
> producer exists.

## Host Runtime Config Templates (`templates/host/`)

These three templates configure the **host runtime** — the coding assistant and the developer's own
profile — rather than producing `.planning/` state, so W019 does not apply to them and they are not
canonical artifacts of this registry.

| Template | Read by | Emits to | Purpose |
|----------|---------|----------|---------|
| `host/copilot-instructions.md` | `bin/install.js` (Copilot install surface) | `<configDir>/copilot-instructions.md`, repo-root `AGENTS.md` | GSD instructions merged into Copilot's instruction file |
| `host/dev-preferences.md` | `gsd-tools generate-dev-preferences` | `skills/gsd-dev-preferences/SKILL.md` | Developer behavioural directives derived from session profiling |
| `host/user-profile.md` | `gsd-tools write-profile` | `USER-PROFILE.md` | Developer behavioural profile report |

> **`CLAUDE.md` has no template file.** `.planning/CLAUDE.md` *is* a canonical `.planning/` root
> artifact (it is in `CANONICAL_EXACT`), so its row stays in the root table above and W019 keeps
> recognising it. It is assembled in code — `generate-claude-md` in `src/profile-output.cts` — so
> there is nothing under `host/` for it; the former `claude-md.md` template was unreachable and was
> removed upstream (#4139).

> **The emitted destinations did not move.** Relocating a template changes where the installer and
> `gsd-tools` *read* from, never where they *write* to. Copilot CLI discovers
> `copilot-instructions.md` at the install root; moving that destination would break instruction
> discovery for every Copilot user.

> **`dev-preferences.md` names two different files.** The template here is GSD-shipped input. The
> `dev-preferences.md` that `bin/install.js` preserves during legacy cleanup is a *user-authored*
> file in the installed command directory — an unrelated artifact that must never be repointed at
> this template.

## Adding a New Canonical Artifact

When a new workflow produces a `.planning/` root file:

1. Add the file name to `CANONICAL_EXACT` in **`src/artifacts.cts`** — the `.cjs` under
   `gsd-core/bin/lib/` is its tsc output and is gitignored (ADR-457); editing it is wasted work
2. Add a row to the **`.planning/` Root Artifacts** table above
3. Add the template to `gsd-core/templates/` if one exists

## Adding a New Template

When a new template file is added under `gsd-core/templates/`:

1. Author its `gsd-template:` block per [`docs/reference/template-registry.md`](../../docs/reference/template-registry.md).
   There is no default and no null — all five keys are required, and `npm run lint:generated-sync`
   fails on a template that has no block.
2. Run `npm run regen:derived` to refresh `docs/TEMPLATE-REGISTRY.json` and the Template Index above.
   Never hand-edit the region between the markers.
3. If the template's leading `---` block is the **artifact's** frontmatter (as in `VALIDATION.md`,
   `SECURITY.md`, `UI-SPEC.md`), the registry block is a **separate second block**. Never merge it in:
   agents copy that first block into produced planning state, so a merged key would be stamped onto
   every artifact the template produces, in every project.
