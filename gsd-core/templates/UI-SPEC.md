## Design Contract (`.pen`)

> Fill this section ONLY if the repository has an extracted design contract
> (`**/*.contract.json`). Otherwise write `Not applicable — no .pen design file`
> and move on; most repositories have none.

Node ids come from the contract, not from the design file by eye. Refresh it with the
repository's own extractor (command from the contract or the project docs), then read
the JSON. One repo's convention, as an example only:

```bash
bun tools/ui-system/extract-pen-contract.ts <file.pen>   # refresh, then read the JSON
```

| Component | `nodeId` | Screens | States in contract | States in scope |
|-----------|----------|---------|--------------------|-----------------|
| {DeckCard} | {r0EHL} | {SCR-20, SCR-21} | {default, loading, empty, archived} | {default, loading, empty} |

**Why `nodeId` and not the component name:** names in a design file change, ids do
not. The id is what lets a checker verify the claim instead of trusting prose —
`gsd-ui-checker` Dimension 8 fails a spec that says "matches the mockup" where a
contract exists.

**States out of scope** must be listed with a reason. A component shipped with three
of five states looks finished until someone hits the missing arc.

**Tokens:** where the contract stores a token reference (`$space-3`,
`$color-surface-base`), the implementation uses the token — not the literal value it
currently resolves to. Literals are design-system drift and are scored against the
Color/Spacing pillars in review.
