# Токены и визуальный язык

Содержимое зоны `01 Foundation` и правила, по которым на него ссылаются остальные уровни (`frame-hierarchy.md` — дерево целиком).

## Токены: 3 тира
`primitive → semantic → component`:
- **primitive** хранит значение: `purple-500 #9225B2`, `space-4 16`.
- **semantic** хранит намерение: `color-bg-surface`, `color-text-danger`, `space-inset-md`.
- **component** локальные решения: `button-primary-bg`.
Ноды ссылаются на **semantic** (или component), не на primitive напрямую и не на хардкод-hex. Так рефактор значения/темы безопасен.

Naming на semantic/component — «зачем», а не «что»: `color-text-danger`, не `color-red`. Темизация (light/dark, density, platform) — переопределением semantic-токенов: primitives хранят все значения обеих тем, component ссылается на semantic и меняется вместе с ним. Компонентный токен, которому нужны разные значения по темам, — признак того, что не хватает semantic-токена: заведи его и сошлись.

## Namespace-канон (когда есть дрейф)
Если в файле два namespace одного смысла (легаси-набор и semantic `color-*`) — выбери ОДИН канон (обычно semantic) и привяжи легаси-алиасы к нему: alias-переменная = ссылка на другую переменную (например `color-border: $legacy-border`). Сначала **вырави значения** (если расходятся — решение владельца, какое канон), потом миграция ссылок становится lossless и может идти постепенно. Связь с кодом: имена токенов 1:1 с CSS-переменными для механического хэндофа — но направление код→дизайн (диагностика дрейфа), не наоборот.

## Spacing
Шкала на базе 4/8: 0,4,8,12,16,20,24,32,40,48,64,80. Каждый gap/padding — токен из шкалы; сырые 13/18/22 = баг. Padding на тексте обычно запрещён — обернуть во frame. Радиусы — своя шкала; вложенность концентрическая (inner = outer − padding).

## Типографика
Шкала ступенями, а не произвольными размерами. Рабочий набор для продуктового UI (px): `12 · 14 · 16 · 20 · 24 · 32 · 40 · 48`. Body — **16** (14 допустим для плотных таблиц и вторичного текста, ниже 12 не опускаться). Соседние ступени различимы: два стиля с разницей в 1px — это один стиль.

- **Line-height** обратно пропорционален размеру: body 1.4–1.6, заголовки 1.1–1.25. Крупный текст с body-интерлиньяжем выглядит разреженным, мелкий с заголовочным — слипается.
- **Веса** — минимум различимых: regular 400 + medium 500 + semibold/bold 600–700. Четыре и больше веса в продуктовом UI обычно не читаются как система.
- **Токен = роль, не размер:** `text-body`, `text-caption`, `text-heading-lg` — но не `text-16`. Переименование размера не должно требовать правки всех ссылок.
- **Длина строки** для читаемого текста — 45–75 символов; шире — глаз теряет строку при переносе.
- **Табличные цифры** (`tabular-nums`) для цен, метрик, идентификаторов: пропорциональные цифры прыгают при обновлении и ломают выравнивание колонок.
- **Оптический размер заголовков** зависит от брейкпоинта: H1 в 40px на 1440 становится 28–32px на 390. Шкала одна, но роли переназначаются по брейкпоинту.

## Контраст и a11y (закладывать сразу — потом дорого)
- WCAG AA: 4.5:1 для body, 3:1 для крупного/UI. Серый «secondary» на белом часто ~3.5:1 → не для body (затемнить).
- Accent на белом обычно ~2:1 → не текст акцентом на белом (акцент — фон под near-black).
- Таргеты — порог в чеклисте `SKILL.md` → «Когда работа закончена»; фокус виден; смысл не только цветом; один H1.

## Anti-generic-AI-look
- Карточку заводи там, где нужна граница кликабельной сущности; мета и вторичный текст живут plain text'ом. Один accent на экран. Градиент и тень появляются, когда решают задачу (глубина, разделение), а не для украшения. Mixed radii — намеренно.
- Реальные данные вместо lorem — настоящие примеры из домена проекта (бери из DESIGN-SYSTEM.md / реальных данных), а не «Lorem ipsum» и не плейсхолдер-имена. Табличные цифры (цены/идентификаторы/метрики) — mono/семантический стиль. Оптическое центрирование.
- Тени сдержанно (плоская board-UI): карточка живёт на границе ИЛИ тени, не на обоих. Анимировать только transform+opacity.

## Состояния (на каждый data-экран)
`happy · loading(skeleton) · empty(first-use + user-cleared) · no-results · error · offline`. Skeleton повторяет точную сетку (не центр-спиннер) — снижает воспринимаемое ожидание и убирает layout-shift. Каждое пустое/ошибочное состояние отвечает на «что теперь?» — текст + явное действие. `empty` расщепляется на два случая: **first-use** (данных ещё нет — объясни ценность и дай первое действие) и **user-cleared** (пользователь сам всё удалил — предложи вернуть или создать заново); в сетке состояний это две ячейки, не одна.

Guest vs authorized — не эта ось, а роль/контекст: `frame-hierarchy.md` → «Две оси состояний».
