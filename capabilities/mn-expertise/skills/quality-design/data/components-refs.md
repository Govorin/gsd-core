# Компоненты, ref, single-source-of-truth

Цель: правка компонента должна расходиться везде автоматически (один Update вместо N). Это главный рычаг дешевизны правок.

## Базовые правила
- Любой повторяющийся UI — компонент (`reusable:true`). На экранах — только инстансы (`ref` на источник), НЕ копии вёрстки.
- **Источники живут в Kit-зонах:** общие — в `02 UI Kit`, нужные одной фиче — в её `[kit] <Feature>` (граница между ними — `frame-hierarchy.md` → «Два уровня Kit»). Среди экранов источников нет — только `ref`; исключение — screen-source (ниже). Источник вне Kit-зон = будущий дубль и дрейф.
- Окупаемость (rule of three): выносить в компонент при ≥3 повторах ИЛИ ≥2 состояниях. Раньше — преждевременно (мусор в библиотеке); позже — пойдут detach-копии.

## Состояния через ref+override (НЕ копии)
Один источник-экран = happy (`reusable:true`). Каждое состояние канона (`happy · loading · empty · no-results · error · offline` — см. `visual-language.md` → «Состояния») = `ref` на него + override:
- `loading` → replace контентного слота на skeleton;
- `empty`/`error`/`no-results`/`offline` → replace контента на соответствующий фрейм;
- `guest`/`authorized` → override шапки на нужный источник.
Override без `type` = патч свойств; с `type` = полная замена поддерева (слоты). «Удаление» узла в инстансе = `enabled:false`, не Delete.
Почему: standalone-копии состояний = N правок при изменении happy. ref+override = одна правда. Какие состояния обязательны и как их рисовать — `visual-language.md` → «Состояния».

## Variants vs slots
- Меняется только оформление/состояние при той же роли → **variant** (свойство компонента).
- Меняется назначение/структура → **отдельный компонент** или **slot** (композиция).
- Правило: «общее — конфигурируемым, необычное — композируемым». Лавина boolean-пропов = сигнал, что нужен slot.
- Нужна вариация → добавь свойство/variant/slot. Если тянет детачить — это недостающее свойство в компоненте, а не повод отвязывать.

## Форма ref+override (пример; сверь со схемой инструмента)
Инстанс ссылается на источник по id; override вложенной ноды адресуется по её id/пути. Концептуальная форма (имена полей зависят от инструмента):
```
{ type:"ref", ref:"<sourceId>",
  descendants:{
    "<childId>": { fill:"$color-brand" },              // патч свойств (без type)
    "<slotId>":  { type:"frame", name:"Skeleton", ... } // полная замена поддерева (с type)
  } }
```
Без `type` = патч свойств; с `type` = замена узла целиком (слот). «Скрыть» узел в инстансе → `enabled:false` в его override, не Delete.

## Screen-sources (исключение)
Полноэкранный макет, выступающий источником состояний экрана (happy-экран `reusable:true`), — это L2, его место в зоне `03 Features` рядом со своими состояниями, НЕ в Kit. Это одно из трёх легальных мест для источника (`frame-hierarchy.md` → «Инварианты дерева»): Kit-зоны держат компоненты (атомы/молекулы/организмы), `03 Features` — экраны. Audit должен считать нарушением источник вне всех трёх мест, а screen-source рядом со своими состояниями — нормой.

## Retirement legacy-компонентов (несколько поколений)
Когда есть старый и новый компонент одного назначения (дрейф поколений):
1. **Freeze** — пометить старый `deprecated` (аннотация в Kit). Не удалять.
2. **Migration Audit** — найти все инстансы старого (по refs).
3. **Parity Check** — убедиться, что новый имеет весь набор детей старого (иначе repaint потеряет функции — частая ошибка с authorized-вариантами, у которых детей больше).
4. **Repaint** — переключить инстансы на новый. ВНИМАНИЕ: если `Update` не меняет `ref` (типично), repaint = Delete старого инстанса + Copy нового на его место; перед этим проверь, что на id инстанса нет внешних ссылок (флоу!).
5. **Archive/Delete** — старый в Archive-зону после подтверждения нуля инстансов.
Порядок обязателен: сначала перепривяжи все инстансы, дождись нуля ссылок на старый источник — и только тогда удаляй. Обратный порядок оставляет orphan-refs.

## Витрина компонентов (Kit)

Структура зоны и её место в дереве файла — `frame-hierarchy.md`. Здесь — как наполнять секцию компонента.

**Навигация по функциональным секциям** (Primitives/Navigation/Forms/Cards/Feedback/Overlays/Media/Brand), не по чистому atomic-уровню: «в какой атом идёт DatePicker?» — плохой вопрос, на который команда отвечает по-разному каждый раз. Функция («это форма») опознаётся однозначно.

### Анатомия секции компонента

Одинаковая у всех — предсказуемость важнее выразительности:

1. **Section Header** — имя (совпадает с именем в коде), одна строка назначения, статус (`stable/beta/deprecated/coming-soon`), ссылка на реализацию.
2. **Specimen Grid** — строки = варианты, колонки = interaction-состояния (`frame-hierarchy.md` → «Interaction-состояния: что рисовать»).
3. **[anatomy]** — опц.: увеличенный экземпляр с выносками токенов (какой padding, какой radius, какой цвет). Окупается на компонентах, которые часто собирают заново.
4. **[do-dont]** — опц.: пара «правильно / неправильно» рядом. Одна пара, бьющая в реальную ошибку команды, полезнее пяти абстрактных.

### Практики наполнения

- **Имя = имя в коде.** `Button`, а не «Кнопка синяя». Расхождение имён — главный источник «дизайнер и разработчик говорят о разном».
- **Реальный контент в специменах.** Настоящие названия товаров, реальные суммы, живые email — на них видно то, чего не видно на «Lorem»: переполнение, перенос, выравнивание цифр.
- **Крайние случаи рядом с нормой.** Самая длинная строка, самое большое число, пустое значение, отсутствующая аватарка. Компонент, проверенный только на идеальных данных, сломается на первом же экране.
- **Плотность.** Секции — с одинаковыми отступами и выравниванием по сетке: витрина сама себе пример визуального ритма.
- **Статус честный.** `beta` у того, что ещё поедет; `deprecated` — с указанием замены (`Retirement` ниже). Kit, где всё «stable», не читают.
- **Responsive-варианты одного компонента — рядом** в одной секции, одинаковый контент → дрейф между брейкпоинтами виден глазом.
- **Композиция — тоже экспонат.** Как Field + Button собираются в Form Row, как карточки образуют сетку. Компоненты по отдельности не отвечают на вопрос «как их сочетать».
- **Заводи компонент по порогу**, а не заранее (rule of three выше). Kit, набитый впрок, — это библиотека, которую никто не помнит целиком.
