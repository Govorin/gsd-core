# Процесс, контекст-дисциплина, многосессионность

## Маленькие пачки, частые вехи
Большие правки — пачками (потолок и его причина — `canvas-gotchas.md` → «batch и операции»), verify после каждой секции, git-веха после каждого подтверждённого сохранения. Доводи каждую пачку до сохранения: несохранённый in-memory теряется при сбое и не откатывается поузлово.

## Сверяйся с владельцем (но не чрезмерно)
Перед НЕОБРАТИМЫМИ или массовыми мутациями (удаление узлов, перенос десятков, смена значения токена на сотнях узлов) — короткий вопрос владельцу, особенно про судьбу узлов (удалить/архивировать/оставить). Это дёшево и предотвращает дорогую ошибку. Там, где решение уже принято или дефолт очевиден — действуй и сообщай результатом.

## Владелец судит по визуалу, не по данным
- Если он говорит «криво» — НЕ спорь замерами/JSON. Воспроизведи его восприятие скриншотом нужного места, найди проблему на нужном уровне вложенности.
- Структура в данных (правильные имена, ref) ≠ хороший вид на холсте. Вывод «хорошо» делай, посмотрев глазами хотя бы ключевые места; JSON подтверждает структуру, а не вид.
- Скриншоты — экономно (дорого по контексту/времени), но для проверки «было криво → стало ровно» они оправданы. Это не противоречие «verify через данные»: данные ловят структурные дефекты, скриншот — визуальные/восприятие.
- Владелец активно дорабатывает файл между сессиями — твой контекст устаревает. ВСЕГДА перечитывай живой файл перед работой, не доверяй своему прошлому представлению.

## Контекст-дисциплина и делегирование
- Объёмную аналитику/проектирование (инвентарь компонентов, расчёт раскладки, сбор источников) делегируй субагенту — он вернёт компактный план/маппинг, ты выполнишь. Не таскай деревья узлов в свой контекст.
- Мутации веди сам single-writer с verify — на multiplayer-файле параллельные писатели ловят race; геометрия холста НЕ модель изоляции (единица конфликта — id-граф, особенно общая Kit-зона). Параллель безопасна только для read-only стадий или непересекающихся по id зон.
- Чтение — дёшево (CLI-парсер по диску для baseline; read-tool для live). Скриншот — точечно. Результаты субагентов — summary-only.

## Многосессионность
Держи три уровня страховки: **git-вехи** (откат), **память проекта** (что сделано/осталось, факты, грабли — авто-подгружается в новую сессию), **resume-промпт** (детальный бриф с тем, чего нет в файлах: живые грабли, решения по узлам, нюансы процесса). В новой сессии: прочитать память + DESIGN-SYSTEM.md + git log → сверить с живым файлом замером → продолжать.

## Скептичность к артефактам
Старые доки/скилы/комментарии в файле врут (устаревшие цифры, ложные «факты» вроде «файл зашифрован»). Источник истины — живой файл, проверенный замером, и DESIGN-SYSTEM.md проекта (если он поддерживается актуальным). Один авторитетный дизайн-док; не плодить параллельные.

## Чеклист самопроверки — что делать с найденным
Сам чеклист (продуктовый + технический блок) — в `SKILL.md` → «Когда работа закончена». Здесь — как читать его пункты.

**Пред-полётный чеклист экрана** (`вход · цель · контекст · состояния · выход · удобство`) — тот же продуктовый блок, заданный ДО вёрстки. Два пункта, которых нет в пост-проверке:
- **контекст** — что пользователь уже знает и с чем пришёл (данные, устройство, спешка); задаёт плотность экрана и объём подсказок.
- **состояния** — какие из канона реально возможны на ЭТИХ данных: список, который не бывает пустым, не нуждается в empty; экран без запроса — в loading.

Остальные пункты читаются по формулировкам чеклиста в `SKILL.md`; «нет ответа» на любой = экран недопроектирован, вёрстку не начинай.

**Что делать с найденным:** чинить обновлением (`Update`), не delete-and-recreate — пересоздание меняет id и рвёт refs. Пункт, который не проходит, но требует решения владельца (судьба узлов, выбор канона токенов) — не чини молча, спроси.
