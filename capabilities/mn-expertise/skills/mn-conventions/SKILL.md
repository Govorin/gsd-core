# mn — рабочий процесс

Этот скилл про **процесс**: что запустить, что не коммитить, куда пойти за правилом.
Правил написания кода здесь нет намеренно — они разъедутся с источником, если их дублировать.

## Куда идти за правилом

Три источника, у каждого своя роль. Открывай тот, что отвечает на твой вопрос — не гадай по памяти.

| Вопрос | Источник |
|---|---|
| Куда положить файл, что кому можно импортировать, границы слоёв | скилл **mn-architecture** |
| Как писать: Either-цепочки, ts-pattern, branded ID, сигнатуры | скилл **quality-typescript** |
| **Почему** правила именно такие: вывод из SOLID, strict, `z.infer` | `docs/architecture/quality-typescript.md` |
| Полный стандарт: слои, модули, тесты, именование, энфорсмент | `docs/architecture/`, навигация в его `README.md` |
| Синтаксис DI, команды NX, стек | корневой `CLAUDE.md` |
| Структура NX, генераторы | скилл **nx-workspace** |
| Схема БД, миграции, запросы | скилл **drizzle-orm** |

Если пишешь TypeScript — открой `quality-typescript` и `mn-architecture` до первой строки кода,
а не после ревью. Оба дешёвые: первый даёт форму, второй — место.

## Что здесь остаётся: Library-First

Единственное правило раскладки, которое живёт в этом скилле, потому что оно про **процесс принятия
решения**, а не про слои.

Приложение — это composition root: DI-проводка, bootstrap сервера, роутинг, и почти ничего больше.
Бизнес-логика живёт в `libs/`.

**Почему**: код в `apps/` заперт внутри одного приложения. Тот же сервис в `libs/` доступен любому
приложению, тестируется без поднятого сервера и переезжает в отдельный процесс подменой строки
регистрации.

**Это норматив, а не описание.** Репозиторий от него далёк: в `apps/` сегодня втрое больше кода,
чем в `libs/`. Практический смысл правила — не переписывать существующее, а **не увеличивать
расхождение**: новая логика идёт в библиотеку, даже если рядом в `apps/` уже лежит похожая.

**Как думать**: «это можно вынести в библиотеку?» — если да, оно и должно быть там. Куда именно
внутри `libs/` и как назвать — вопрос к `mn-architecture`, там же правила именования и алиасов.

## Quality gate — перед каждым коммитом

Блокирующая проверка. Не коммить код, который её не проходит: сломанный `main` стоит дороже
любой скорости, потому что чинить его будет не тот, кто сломал.

```bash
# 1. NX-проекты из staged-файлов
STAGED_TS=$(git diff --cached --name-only -- '*.ts' '*.tsx')
PROJECTS=$(echo "$STAGED_TS" | while IFS= read -r f; do
  dir=$(dirname "$f")
  while [ "$dir" != "." ] && [ "$dir" != "/" ]; do
    [ -f "$dir/project.json" ] && grep -o '"name"[[:space:]]*:[[:space:]]*"[^"]*"' "$dir/project.json" | head -1 | sed 's/.*"\([^"]*\)"$/\1/' && break
    dir=$(dirname "$dir")
  done
done | sort -u | tr '\n' ',' | sed 's/,$//')

# 2. ОБЯЗАТЕЛЬНО: пустой список — не «нечего проверять»
if [ -z "$PROJECTS" ]; then
  echo "⚠ NX-проектов в staged нет. Возможные причины:"
  echo "  · ничего не добавлено в индекс (git add)"
  echo "  · правки только вне libs/ и apps/ — корневые конфиги, docs, скрипты"
  echo "  Прогонять нечего; если тронуты tsconfig.base.json / nx.json / .oxlintrc.json —"
  echo "  нужен более широкий прогон, выбери проекты вручную."
  exit 0
fi
echo "Проверяю: $PROJECTS"   # сверь глазами: мусор здесь = зелёный гейт при нуле проверок

# 3. Линт (oxlint — быстрый, обычно <1s)
npx nx run-many -t lint -p "$PROJECTS"

# 4. Тайпчек (инкрементальный tsc)
npx nx run-many -t typecheck -p "$PROJECTS"

# 5. Оба зелёные → только теперь git commit
```

⚠️ **Почему guard обязателен, а не вежливость.** `nx run-many -p ""` не «ничего не делает» — он
запускает цель для **всего воркспейса** (проверено: 248 проектов) и возвращает `0`. Три обычных
сценария приводят сюда: пустой индекс, правка корневого конфига, правка не-TS файла. Итог — либо
долгое ожидание, либо чужие ошибки, которые агент по правилу «чини и то, что было до тебя»
начнёт править вместо своей задачи.

⚠️ **Зелёный ≠ проверено.** Цели `lint`/`typecheck` есть не у всех проектов, а `nx run-many` на
несуществующем имени тоже отвечает `0` и «No tasks were run». Поэтому список печатается перед
прогоном — если сомневаешься, что цель есть, посмотри `nx show project <имя>`.

**Если упало** — не коммить. Починить, `git add` правки, прогнать заново. Ошибки, которые были до
тебя, тоже чинятся: иначе они переезжают в следующий PR и превращаются в «так было всегда».

**После завершения плана целиком** — полный прогон, включая сборку и тесты:

```bash
npx nx run-many -t lint,typecheck,build,test -p "$PROJECTS"
```

### Правила прогона

- **Новых подавлений не добавлять.** `@ts-ignore`, `@ts-expect-error`, `oxlint-disable`, `@allow-*`
  превращают пойманную ошибку в ненайденную: отчёт зеленеет, дефект остаётся. Чинится код, а не
  отчёт о нём.
  В репозитории таких пометок уже сотни — это долг, а не образец: **существующие не тиражируй**,
  не копируй строку с подавлением в новый файл «по аналогии».
  Если чинить действительно нечего (баг в типах чужой библиотеки, несовместимость версий) — годится
  `@ts-expect-error` с одной строкой причины рядом: он сам станет ошибкой, когда апстрим починят,
  и подавление не переживёт свою надобность. Глухой `@ts-ignore` так не умеет — поэтому его не бывает
  оправданно.
- **Быстрый тайпчек** — `bunx tsc --noEmit -p <проект>/tsconfig.lib.json` вместо `nx build`, когда
  нужен только тип: сборка делает лишнюю работу. Файл называется так не везде (у приложений —
  `tsconfig.app.json`, у части либ его нет вовсе); если не нашёлся, посмотри `nx show project <имя>` —
  путь указан в опциях цели `typecheck`.
- **NX не запускать в фоне.** Фоновые процессы копятся между сессиями и подвешивают машину.
  Рецепт очистки не дублирую — он в корневом `CLAUDE.md` → «NX Performance Rules (CRITICAL)»,
  и там же полный список путей кэша. ⚠️ `pkill -f nx` матчит любой процесс, где встречается `nx`,
  включая собственный шелл агента — сужай паттерн.
- **Python — свой тулчейн.** `uv run ruff check`, `uv run pyright`; Biome и oxlint `.py` не трогают.
  ⚠️ `uv run ruff` резолвится в разную версию в зависимости от рабочей директории — при странном
  вердикте сверь `uv run ruff --version` в корне и в пакете.

## Чеклист перед сдачей работы

Скопируй и отметь. Пункты, требующие правила, отсылают к владельцу — проверяй там, а не по памяти.

```
- [ ] Quality gate зелёный, и в списке проверенных — те проекты, что правил
- [ ] Логика в libs/, в apps/ только проводка
- [ ] Файл в правильном слое, импорты границ не пересекают   → mn-architecture
- [ ] Ошибки — значения; ветвление через .exhaustive()       → quality-typescript
- [ ] Тесты рядом с кодом (*.spec.ts), не в __tests__/
- [ ] Прогнал по изменённым файлам (F = список файлов из git diff --cached):
      grep -n ': any\|as any' $F          # явный any
      grep -n 'ts-ignore\|oxlint-disable' $F   # новые подавления
      grep -n 'export \* from' $F         # ре-экспорты
```

Последний пункт вынесен в команды не для формальности: линта на эти три вещи нет, и «проверил
глазами» на файле в триста строк означает «не проверил». Три `grep` занимают секунду и дают
однозначный ответ — в отличие от впечатления.

Пункты «DTO без дублей» и «один файл — одна сущность» в чеклист не вынесены намеренно: механически
они не проверяются, а невыполнимый пункт обесценивает соседние. Это предмет ревью, а не гейта.
